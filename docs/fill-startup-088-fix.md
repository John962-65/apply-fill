# v0.8.8：扫描到字段后，AI 还没启动就中断

用户截图显示 v0.8.7 扫描到 103 个字段、成功填写 0 个，AI 匹配、API 和填写均未执行，状态是“目标已变化或被遮挡，未点击”。这说明失败发生在匹配前的控件选项预读阶段。顶部“ApplyFill 已开始调试此浏览器”是浏览器输入通道的正常提示。

## 原因

`handleAiFillClick` 在发送 AI 请求之前调用 `prefetchComboOptions`。旧版没有在每个控件的预读操作周围捕获异常；一次点击被拒绝后，异常会直接进入整轮填写的错误处理，其他字段也无法继续。原诊断未记录预读耗时和阶段，浏览器定位失败又被合并成同一条错误，因此只显示 `unknown`。

另一个问题是 Phoenix 的触发位置：`@beisen-phoenix/select@3.3.55` 的 `src/components/Select.tsx` 将 `onWrapperClick` 挂在 `.phoenix-select` 外层，内部 `__inputWrapper` 只是宽度可变的输入布局。`__placeHolder` 是独立的绝对定位兄弟节点；内部输入区域的中心点可能命中这个显示层，旧版因此拒绝点击。

公开源码：[npm 3.3.55](https://www.npmjs.com/package/@beisen-phoenix/select/v/3.3.55)、[发布源码包](https://registry.npmjs.org/@beisen-phoenix/select/-/select-3.3.55.tgz)。实际站点仍可能使用其他版本或定制样式。

## 修复

- 每个下拉分别处理预读失败，始终尝试收起自己关联的面板，然后继续下一字段。失败的词表仍标记为“尚未观察、并非完整”，不把空数组当作网站没有可选项。
- 页面已有内容的控件不再为了预读重复打开；已有值保护继续生效。
- Phoenix 优先使用实际 `.phoenix-select` 触发容器，同时兼容 `__cont` 结构。页面重新渲染后仍须按唯一字段身份重新定位。
- 浏览器点击在目标矩形内检查最多九个位置，找到确实命中目标或其内部节点的位置后才点击。完全遮挡、目标不唯一、目标已替换或禁用时拒绝操作。鼠标移动后再次检查，避免悬停事件替换控件后点击旧坐标。
- 浏览器操作返回固定错误类别，如 `input_target_covered`、`input_target_missing`、`input_attach`，不把网页异常原文复制进诊断。
- 诊断增加中断阶段、选项预读耗时、尝试数、读到选项数、失败数和失败类别。字段对照表会标出具体哪一项预读未完成。

## 验证范围

匿名复现场景包含 103 个字段、人工已有内容、一个被完全遮挡的下拉和一个输入占位区被兄弟显示层覆盖的 Phoenix 下拉。使用真实 Chromium 浏览器输入、生产扫描和填写控制器，以及生产 AI 来源校验；模型响应和 Chrome 存储是测试替身。

- 使用交付的 v0.8.7 代码复现：第一个控件点击失败后，AI 请求次数为 0，其他字段保持空白。
- 修复后：遮挡控件保持未填、没有点击遮罩；AI 能启动，后续姓名、邮箱及语言写入，人工备注保留，未提供来源的 98 项补充字段保持为空。
- 第一次浏览器连接失败时：单独记下预读失败，后续匹配及可用控件继续执行。
- AI 匹配失败时：诊断显示匹配阶段和网络错误，并保留先前预读统计；填写按钮恢复可用。
- 浏览器输入覆盖中心遮挡但有可用区域、完全遮挡、悬停后替换、中文输入和重复输入。
- 单元检查及原有 Phoenix、通用下拉、日期、来源校验和采集回归用于核对其他流程。

这些是公开组件与匿名测试页的验证，没有登录用户截图中的招聘页面。完全遮挡或无法唯一确定身份的控件仍会单独报告失败。

本轮 96 项单元检查全部通过；上述三个启动场景、12 个 Phoenix 场景、完整填写、通用表单与下拉、ATSX 日期、真实公开组件日期及下拉、控件采集、自动点击采集和管理界面回归均通过。

## 更新

解压 v0.8.8，覆盖原扩展目录，在扩展管理页重新加载，再刷新招聘网页。资料树、模板和 AI 配置不需要重新导入。启用“实验：浏览器层点击与输入”，运行时保持招聘页在前台。

浏览器检查可运行 `npm run test:startup`；该检查需要安装 Playwright 对应的 Chromium。
